# ยกเลิกออเดอร์ที่ไม่จ่ายเงินอัตโนมัติ (store v2)

## ทำไม

ร้านเคยเจอลูกค้าแย่งชิ้นสุดท้ายกันจริง ระบบตอนนี้กันขายเกินได้แล้ว (`create_order` ใช้ `BEGIN IMMEDIATE` + `UPDATE ... WHERE stock >= ?`) แต่ตัดสต็อกตั้งแต่ตอนสร้างออเดอร์ (`pending_payment`) และไม่มีอะไรปล่อยของคืนเลย ถ้าคนที่ได้ชิ้นสุดท้ายไม่โอน ของจะถูกกันไว้จนกว่า staff จะกดยกเลิกเอง คนที่อยากจ่ายจริงก็เห็น "หมด" อยู่ตลอด

เป้าหมายคือให้ของที่จองไว้แต่ไม่จ่ายกลับมาขายได้เอง โดยไม่ทำให้ลูกค้าที่โอนจริงแต่อัปสลิปช้าเสียเงินฟรี

## เป้าหมาย

1. ออเดอร์ `pending_payment` ที่เกินเวลาที่ตั้งไว้ จะถูกปิดอัตโนมัติและคืนสต็อก
2. admin เปิด/ปิดระบบนี้ได้ และตั้งเวลาได้ที่หน้า `/admin/settings` (ค่าเริ่มต้น: ปิด, 60 นาที)
3. ลูกค้าเห็นนับถอยหลังในหน้าอัปสลิป `/order/[code]`
4. ออเดอร์ที่หมดเวลายังรับสลิปได้ ทั้งจากลูกค้าในหน้าออเดอร์ และจาก staff ที่อัปแทนจากหลังร้าน
5. สลิปที่มาช้า: ถ้าของยังเหลือ ให้จองคืนอัตโนมัติ ถ้าหมด ให้เข้าคิวคืนเงินให้ staff ดำเนินการ

## ไม่ทำ

- ไม่แตะออเดอร์ FP28 หรือ `server/fp28/` ระบบ FP28 เดิม
- ไม่จองของตอนใส่ตะกร้าหรือตอนเข้าหน้า checkout (ยังตัดสต็อกตอนกดสั่งซื้อเหมือนเดิม)
- ไม่ส่งแจ้งเตือน (อีเมล/LINE) ตอนใกล้หมดเวลาหรือหมดเวลา
- ไม่ยืดเวลาให้รายออเดอร์

## ห้ามเกิด (ถือว่าล้มเหลวแม้ระบบจะทำงาน)

- ระบบปิดออเดอร์ที่อัปสลิปแล้ว (`waiting_confirm` ขึ้นไป) ต้องปิดเฉพาะ `pending_payment` เท่านั้น
- ลูกค้าโอนเงินแล้ว แต่ไม่มีทางส่งสลิปหรือติดต่อร้านได้
- สต็อกถูกคืนซ้ำ หรือติดลบ (ระบบปิดพร้อมกับ staff กด หรือสลิปมาพร้อมกับระบบปิด)
- ยอดขายใน dashboard นับออเดอร์ที่หมดเวลาหรือคืนเงินแล้ว
- เปิดระบบครั้งแรกแล้วออเดอร์ค้างเก่าถูกปิดพร้อมกันหมดโดยที่ staff ไม่รู้มาก่อน (ดูข้อ "เปิดระบบครั้งแรก")

## สิ่งที่ตัดสินแล้ว (จากผู้ใช้)

- ระบบเปิด/ปิดได้ และ admin ตั้งเวลาเองได้ ค่าที่พูดถึงคือ 1 ชั่วโมง
- หมดเวลาแล้วลูกค้ายังอัปสลิปได้
- staff อัปสลิปแทนลูกค้าได้จากหลังร้าน (ตอนนี้หลังร้านดูสลิปได้อย่างเดียว)
- สลิปมาช้า + ของยังเหลือ → จองคืนให้อัตโนมัติ
- สลิปมาช้า + ของหมด → staff คืนเงิน
- มีนับถอยหลังในหน้าอัปสลิป
- ข้อความตอนหมดเวลา: "หมดเวลาชำระแล้ว ถ้าโอนแล้วยังอัปสลิปได้ ทีมงานจะตรวจสอบให้ ผ่านทาง https://www.instagram.com/su.mfu/"

## การออกแบบ

### สถานะใหม่

เพิ่ม 3 สถานะใน `ORDER_STATUSES` (`server/store/db.py`) และ `OrderStatus` (`src/types/store.ts`)

| status | ป้าย | ความหมาย |
|--------|------|---------|
| `expired` | หมดเวลาชำระ | ระบบปิดเพราะไม่จ่ายในเวลา สต็อกคืนแล้ว ยังรับสลิปได้ |
| `refund_pending` | รอคืนเงิน | สลิปมาหลังหมดเวลาแต่ของหมดแล้ว รอ staff โอนคืน |
| `refunded` | คืนเงินแล้ว | staff โอนคืนแล้ว (สถานะสุดท้าย เหมือน `cancelled`) |

ไม่ใช้ `cancelled` แทน `expired` เพราะ `cancelled` เป็นสถานะสุดท้าย (`update_order` ไม่ให้เปลี่ยนต่อ) และไม่รับสลิป

การเปลี่ยนสถานะที่อนุญาต:

```
pending_payment ──(หมดเวลา, ระบบ)──▶ expired
expired ──(อัปสลิป + จองคืนได้ครบ)──▶ waiting_confirm   (ตัดสต็อกใหม่)
expired ──(อัปสลิป + ของไม่พอ)──────▶ refund_pending    (ไม่ตัดสต็อก)
expired ──(staff กดยกเลิก)──────────▶ cancelled         (ไม่คืนสต็อกซ้ำ เพราะคืนไปแล้ว)
refund_pending ──(staff)────────────▶ refunded
refund_pending ──(staff กด "ลองจองของอีกครั้ง" เมื่อมีของเข้า)──▶ waiting_confirm
expired ──(staff ยืนยันการโอนทาง IG ไม่มีไฟล์สลิป)──▶ paid   (จองคืนก่อน ของไม่พอ = ไม่ยอมเปลี่ยน 409)
refund_pending ──(staff: สลิปปลอม/ไม่ได้โอนจริง)──▶ cancelled (ไม่แตะสต็อก)
```

- เมนู "เปลี่ยนสถานะเอง" (`src/app/admin/(panel)/orders/[code]/page.tsx`) ซ่อนเมื่อออเดอร์เป็น `expired`/`refund_pending`/`refunded` และไม่มี `expired`/`refund_pending`/`refunded` เป็นตัวเลือกปลายทางจากสถานะอื่น ออเดอร์สามสถานะนี้มีแค่ปุ่มตาม transition ข้างบน
- server (`update_order`) บังคับตารางนี้ด้วย ไม่พึ่งแค่การซ่อนปุ่มในหน้า ส่วนการเปลี่ยนอิสระระหว่างสถานะเดิม (`pending_payment`…`completed`) คงไว้เหมือนเดิม
- **กฎสต็อก:** ทุกครั้งที่ออเดอร์ย้ายเข้าสถานะที่ไม่ถือของ (`expired`, `cancelled` จากสถานะที่ถือของ) ให้คืนสต็อก และทุกครั้งที่ย้ายจากสถานะที่ไม่ถือของกลับไปถือ (`waiting_confirm` จาก `expired`/`refund_pending`) ให้ตัดสต็อก สถานะที่ถือของคือ `pending_payment`, `waiting_confirm`, `paid`, `ready`, `completed`
- ตัวเปลี่ยนสถานะทุกตัวใช้ `UPDATE ... WHERE id=? AND status=?` เหมือน `update_order` ตอนนี้ เพื่อกันคืนหรือตัดสต็อกซ้ำ

### การตั้งค่า

เก็บใน `store_settings` 2 key (ผ่าน `get_settings` / `update_settings` เดิม):

- `payment_expiry_enabled`: `"0"`/`"1"` ค่าเริ่มต้น `"0"`
- `payment_expiry_minutes`: จำนวนเต็ม ค่าเริ่มต้น `60` ช่วงที่ยอมรับ 10–1440 (เดาช่วงเอง ให้ builder ปรับได้)

ในหน้า `/admin/settings` เพิ่มการ์ด "ยกเลิกออเดอร์ที่ไม่ชำระอัตโนมัติ" มีสวิตช์และช่องนาที พร้อมคำอธิบายสั้นๆ ว่าระบบปิดเฉพาะออเดอร์ที่ยังไม่อัปสลิป สต็อกคืนทันที และลูกค้ายังอัปสลิปตามมาได้

**จุดเริ่มนับ (ผู้ใช้ตัดสิน):** เพิ่มคอลัมน์ `payment_clock_started_at` (nullable) ใน `store_orders` ตั้งค่าเป็นเวลาปัจจุบันทุกครั้งที่ออเดอร์เข้า `pending_payment` (ตอนสร้าง และตอน staff ตีกลับด้วยปุ่ม "สลิปไม่ถูกต้อง ให้ลูกค้าส่งใหม่" หรือเปลี่ยนสถานะเองกลับมา `pending_payment`) ลูกค้าจึงได้เวลาเต็มอีกรอบ ออเดอร์เก่าที่ค่าเป็น NULL ใช้ `created_at` แทน (migration ไม่ต้อง backfill)

**เปลี่ยนเวลา:** deadline = `COALESCE(payment_clock_started_at, created_at) + minutes` คำนวณตอนตรวจ จึงมีผลกับออเดอร์ที่ค้างอยู่ด้วย

**เปิดระบบครั้งแรก:** ก่อนบันทึกการเปิด หน้า settings แสดงว่า "มีออเดอร์รอโอน N รายการที่เกินเวลาแล้ว จะถูกปิดทันที" แล้วยืนยันด้วย `useConfirm()` (ตัวเลข N มาจาก API ตอนโหลดการ์ด)

### ตัวปิดออเดอร์อัตโนมัติ

- thread เบื้องหลังใน `order_api.py` รันเฉพาะ primary process เหมือน `run_scheduled_backup` ตรวจทุก 60 วินาที
- logic อยู่ในไฟล์ใหม่ `server/store/expiry.py` (`db.py` ยาวเกินแล้ว) ฟังก์ชันหลัก `expire_unpaid_orders(conn, now) -> list[str]` คืนเลขออเดอร์ที่ปิด ให้ test เรียกตรงๆ ได้โดยไม่ต้องมี thread
- ทำงานใน `BEGIN IMMEDIATE` เดียว: เลือก `pending_payment` ที่ deadline (ข้างบน) ผ่านไปแล้ว → เปลี่ยนเป็น `expired` แบบมีเงื่อนไขสถานะ → คืนสต็อกเฉพาะแถวที่เปลี่ยนสำเร็จ
- `log_audit(conn, code, "v2_order_expired", "auto")` ทุกออเดอร์
- ถ้า thread error ให้ log แล้วรอบหน้าทำต่อ ห้ามให้ thread ตาย
- **กันพลาดตอนลูกค้าเปิดหน้าอยู่:** `attach_slip` ตรวจ deadline เองด้วย ถ้าสลิปเข้ามาตอนออเดอร์ยังเป็น `pending_payment` (thread ยังไม่ทันรัน) ให้รับเป็น `waiting_confirm` ตามปกติ ไม่ต้องสนใจว่าเกินเวลาไปกี่วินาที

### สลิปที่มาช้า (ลูกค้าหรือ staff)

ใช้ฟังก์ชันเดียว เช่น `attach_late_slip` ใน `expiry.py` ที่ทั้ง route ลูกค้าและ route staff เรียก:

1. `BEGIN IMMEDIATE` อ่านออเดอร์ ต้องเป็น `expired`
2. พยายามตัดสต็อกทุกรายการด้วย `UPDATE ... WHERE stock >= ?` เดิม
3. **ได้ครบทุกรายการ** → บันทึกสลิป สถานะ `waiting_confirm` audit `v2_order_revived`
4. **ขาดแม้แต่รายการเดียว** → rollback การตัดสต็อกทั้งหมด (ไม่ได้บางส่วน ตรงกับตอนสั่งซื้อ) บันทึกสลิป สถานะ `refund_pending` audit `v2_order_refund_needed`
5. ทั้งสองกรณีส่ง OCR สลิปเหมือนอัปปกติ (`slips.trigger_ocr_async`)

สินค้าที่ปิดขาย/หมดรอบขายไปแล้ว (`active=0`, `sale_state != open`) ไม่ถือว่าเป็นเหตุให้จองคืนไม่ได้ ถ้ายังมีสต็อก จองคืนได้ เพราะลูกค้าสั่งตอนเปิดขายอยู่และโอนแล้ว *(เป็นการตัดสินของผม)*

### เปลี่ยนสลิปหลังหมดเวลา *(การตัดสินของผม)*

- `refund_pending` รับสลิปใหม่แทนใบเดิมได้ ทั้งลูกค้าและ staff (เผื่ออัปผิดไฟล์) สถานะคงเดิม ไม่พยายามจองของใหม่ (staff ใช้ปุ่ม "ลองจองของอีกครั้ง")
- `cancelled` ไม่รับสลิปเหมือนเดิม staff ที่กดยกเลิกออเดอร์ `expired` คือการตัดสินใจโดยตั้งใจ

### staff อัปสลิปแทน

- route ใหม่ `POST /v2/admin/orders/<code>/slip` (multipart แบบเดียวกับ route ลูกค้า ใช้ `read_multipart_slip`) staff ทุกคนใช้ได้
- ใช้ได้กับ `pending_payment`, `waiting_confirm` (แทนสลิปเดิม), `expired` (ผ่าน `attach_late_slip`) และ `refund_pending` (แทนสลิปเดิม)
- audit `v2_slip_uploaded_by_staff` พร้อมชื่อ staff
- หน้า `/admin/orders/[code]` เพิ่มปุ่ม "อัปโหลดสลิปแทนลูกค้า" ในส่วนสลิป

### หน้าลูกค้า `/order/[code]` (`OrderView.tsx`)

- API ออเดอร์ฝั่งลูกค้าส่ง `paymentDeadline` (ISO มี offset) เมื่อระบบเปิดและออเดอร์เป็น `pending_payment` ไม่งั้นเป็น `null` และส่ง `serverNow` เพื่อชดเชยนาฬิกาเครื่องลูกค้า (นับถอยหลังจาก `deadline - serverNow` แล้วเดินด้วยนาฬิกาเครื่อง)
- **ก่อนหมดเวลา:** แสดง "กรุณาชำระภายใน HH:MM น." (เวลาไทย +7) และ "เหลือ MM:SS" ใกล้ปุ่มอัปสลิป
- **พอนับถึง 0 (ฝั่งหน้า) หรือสถานะเป็น `expired`:** แสดงข้อความที่ผู้ใช้กำหนดพร้อมลิงก์ IG `https://www.instagram.com/su.mfu/` (ลิงก์เดียวกับใน `Footer.tsx` ควรดึงเป็นค่าคงที่ที่เดียว) ปุ่มอัปสลิปยังใช้ได้
- **`refund_pending`:** แสดง "สินค้าหมดระหว่างรอชำระ ทีมงานจะติดต่อคืนเงิน" พร้อมลิงก์ IG
- **`refunded`:** แสดง "คืนเงินแล้ว"
- ข้อความทั้งหมดอยู่ใน `storeI18n.ts` ทั้ง TH/EN ข้อความ EN แปลจากข้อความไทยที่ผู้ใช้ให้มา
- แถบขั้นตอน (`FLOW`) ไม่แสดงสามสถานะใหม่ ใช้ป้ายสีแดง/ส้มแทน แบบเดียวกับ `cancelled`

### หลังร้าน

- รายการออเดอร์: กรองตามสถานะใหม่ได้ `refund_pending` มีป้ายเด่น (ต้องมีคนทำต่อ)
- หน้าออเดอร์: ปุ่มตาม transition ข้างบน และแสดง "หมดเวลาเมื่อ …" สำหรับ `pending_payment` ที่ระบบเปิดอยู่
- ปุ่ม "ลองจองของอีกครั้ง" สำหรับ `refund_pending` ใช้ logic เดียวกับ `attach_late_slip` ข้อ 2–3 (ไม่ต้องมีสลิปใหม่)

### Dashboard / ใบเสร็จ / ส่วนอื่น

- `server/store/dashboard.py` ตอนนี้ไม่นับเฉพาะ `cancelled` ต้องไม่นับ `expired`, `refund_pending`, `refunded` ด้วย (รวมเป็นค่าคงที่ชุดเดียว เช่น `NON_SALE_STATUSES`)
- ใบเสร็จ: ออกได้เฉพาะ `paid`/`ready`/`completed` อยู่แล้ว ไม่กระทบ
- `/check-order` (ค้นด้วยเลขออเดอร์ + เบอร์) แสดงสถานะใหม่ได้ถูกต้อง

## ข้อจำกัด

- ห้ามเขียนข้อมูลออเดอร์จริงนอก flow ที่ออกแบบไว้ ก่อน deploy ครั้งแรกให้ backup DB ด้วย `sqlite3 .backup()`
- `created_at` ของร้านใหม่ (`store_orders`) เก็บเป็นเวลาไทยพร้อม offset `+07:00` (`now_iso()` ใน `server/store/common.py`) ไม่ใช่ UTC แบบ FP28 คำนวณ deadline ต้อง parse offset ห้ามบวก 7 ชั่วโมงซ้ำ `paymentDeadline`/`serverNow` ส่งเป็น ISO ที่มี offset
- ต้อง deploy ทั้ง `api` และ `store` ให้ deploy `api` ก่อน (API ส่งฟิลด์ใหม่เพิ่ม หน้าเดิมไม่พัง) แล้วค่อย `store`

- ปิดเฉพาะ `pending_payment` ที่เกินเวลา ไม่แตะ `waiting_confirm` และไม่ทำอะไรเมื่อปิดระบบอยู่
- คืนสต็อกถูกต้อง และรันพร้อมกับ staff กดยกเลิก สต็อกต้องไม่คืนซ้ำ
- สลิปช้า: ของพอ → `waiting_confirm` และสต็อกลดอีกครั้ง; ของไม่พอบางรายการ → `refund_pending` และสต็อกไม่เปลี่ยนเลย
- สลิปช้าสองใบพร้อมกันแย่งชิ้นสุดท้าย → ได้ `waiting_confirm` ใบเดียว
- `expired` → `cancelled` ไม่คืนสต็อกซ้ำ
- ตีกลับ `waiting_confirm` → `pending_payment` เริ่มนับเวลาใหม่ (ออเดอร์อายุเกินกำหนดไม่ถูกปิดทันที)
- `expired` → `paid` จองของคืน / ของไม่พอได้ 409 และไม่มีอะไรเปลี่ยน
- `refund_pending` → `cancelled` ไม่แตะสต็อก
- server ปฏิเสธการเปลี่ยนสถานะที่ไม่อยู่ในตาราง (เช่น `refunded` → `paid`)
- dashboard ไม่นับสถานะใหม่
- frontend: นับถอยหลังแสดงเมื่อมี `paymentDeadline`, ข้อความหมดเวลา + ลิงก์ IG, ปุ่มอัปสลิปยังกดได้

## ปล่อยให้ builder ตัดสิน

- หน้าตา/ตำแหน่งนับถอยหลังและการ์ดตั้งค่า (ใช้ component เดิมของ admin และหน้าร้าน)
- ช่วงนาทีที่ยอมรับ (เสนอ 10–1440)
- ชื่อฟังก์ชัน/ไฟล์ ถ้ามีเหตุผลดีกว่าที่เสนอ
- จะ refresh หน้าออเดอร์เองตอนนับถึง 0 หรือไม่
